# fork-sync —— 每次 rev → rev 同步的计划与记录

zed-port.md §16 是**索引**，同步的细节都在本目录，一次同步一个文件。

## 为什么这么分

aacode 是 copy-fork（`packages/` 下 167 个 crate 整包搬自 zed，无 merge base）。
换 git rev 只解决「直接依赖 zed 的 29 个 crate」，**不会**让 fork 的源码跟上上游 ——
编译照过，腐化看不见。同步因此是长期工程，需要：

- 能查**现在在做什么**（哪个区间、谁认领了什么）
- 能查**做过什么**（历史批次、当时踩了什么坑、为什么这么切）
- 能**多人分工**而不互相踩（一个 crate 一个 owner）

单次同步的细节会越写越长，所以不放进 §16。

## 文件命名

```
<old7>_<new7>.md          例：bd74733_afecd6d.md = bd747337 → afecd6d719
```

用短 sha 是因为要靠文件名排序看时间线；完整 sha 在文件头的表里。

## 怎么开始一次同步

```sh
just fork-sync new                          # old=当前 pin, new=origin/main
just fork-sync list                         # 看有哪些同步、什么状态
```

`tools/fork-sync-new.sh` 会自动填好：区间提交数、gpui 命中数、命中的 fork crate 清单、
逐条 port 记录（一个上游 sha 一行）、以及 **⚠ 双方都改过的文件**清单。最后一项最重要 ——
这些文件上游动过、aacode 本地也动过，不能盲合，`cargo check` 会过但语义可能错。

生成后**不要立刻覆盖式重写**，已在存在的文件会拒绝生成，继续填就往原文件上加。

## 状态

文件头表格里的「状态」字段：

| 标记 | 含义 |
| --- | --- |
| ⚪ | 计划中（刚生成，没人接） |
| 🟡 | 进行中 |
| 🟢 | 完成（W1/W2/W3 都做完且验收过） |
| 🔴 | 放弃（记原因，别静默删文件） |

认领时在文件名不改的前提下，把「负责人」和 W3 表格里的「认领」列填上名字。

## 目录约定

- 一次同步 = 一个文件，**不合并批次**。批次 A/B/C 是切分单位，各自有 from/to。
- 同一区间重复做（比如中途回滚重来）就再开一个文件，旧的标 🔴 并在「踩的坑」里写明。
- 批次做完后回来更新 zed-port.md §16 的索引表和 §16.2 基线。
